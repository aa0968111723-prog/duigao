# 影片對稿 — 真機驗收清單（PR #23）

自動化測試跑的是 Chromium + 本機 mock。下面這些**mock 測不到**，綠燈也不算過；
每一項都寫了「為什麼這條只有真機能證明」，以及看到什麼算失敗。

## A. Safari（iPhone）：signed URL 的 Range / seek

**為什麼**：`<video>` 拉時間軸是靠 HTTP Range（206 partial content）。Supabase Storage
的 signed URL 曾經有不回 `Accept-Ranges` 的紀錄，Safari 對此特別嚴格——沒有 206 就
整檔下載或根本不能 seek。mock 現在會回 206，所以**它只能證明我們的程式對，不能證明
Storage 對**。

- [ ] iPhone Safari 開分享連結 → 播放
- [ ] 拖時間軸到後半段 → 立刻跳過去，不是等整支下載完
- [ ] 點一個位於後半段的討論卡 → 直接跳到那個時間
- 失敗長相：進度條拖了沒反應、或轉圈很久才動

## B. iPhone 直出的 `.mov`（HEVC）在桌機 Chrome

**為什麼**：`video/quicktime` 裡通常是 HEVC。Safari 播得出來，桌機 Chrome 與部分
Android 播不出來——也就是「主辦方用 iPhone 傳、夥伴用 Windows 開」這個很常見的組合。
程式已經用 `canPlayType` 偵測並給明確說明，但那句話有沒有真的出現只有真機知道。

- [ ] 用 iPhone 相機拍一段，直接上傳（不要先轉檔）
- [ ] 桌機 Chrome 開同一個房間
- 期待：看到「這支是 iPhone 的影片格式…用 Safari 開，或請主辦方輸出成 MP4（H.264）」
- 失敗長相：黑畫面、沒有任何說明

## C. LINE in-app browser

**為什麼**：iOS 的 WKWebView 不允許沒有手勢的自動播放，`play()` 會直接 reject；
LINE 的全螢幕行為也常常是壞的。UA 可以模擬，這些限制不能。

- [ ] 從 LINE 對話點分享連結
- [ ] 卡片顯示的是影片封面＋▶（不是純文字）
- [ ] 進房後看到封面與大播放鈕；**點一下才開始播**
- [ ] 留一則時間點意見、回覆別人的意見
- [ ] 按全螢幕：成功或安靜地沒反應都可以，**不可以卡住或黑畫面**

## D. 未 fast-start 的 MP4

**為什麼**：剪輯軟體預設輸出的 MP4 常把 `moov` atom 放在檔尾，瀏覽器要下載完才知道
長度、才能 seek。Storage 不會幫忙搬。

- [ ] 用「非網頁最佳化」設定輸出一支 MP4 上傳
- [ ] 觀察：時間軸是否很久才有長度、seek 是否要等
- 若明顯很慢：README 已經寫了「請匯出網頁用（fast start）MP4」，確認這句話夠明顯

## E. 三種直向尺寸

**為什麼**：CSS 規則寫好了，但「影片、時間軸、底部工具列同時看得到」是眼睛的判斷。

| 裝置 | 尺寸 | 檢查 |
|---|---|---|
| 小 Android | 360×800 | [ ] 播放器、時間軸、看/修改/討論/更多 同時在畫面上 |
| iPhone 14/15 | 390×844 | [ ] 同上，且直向 9:16 短片不會把工具列擠掉 |
| iPhone Pro Max | 430×932 | [ ] 同上 |

每個尺寸另外確認：

- [ ] 時間軸上的 marker 點得到（手指不是滑鼠）
- [ ] 拖時間軸不會連帶捲動頁面
- [ ] 開啟留言 composer 時鍵盤不會蓋住送出鈕
- [ ] 瀏海／底部手勢條沒有蓋到控制列

## F. 上傳的真實條件

**為什麼**：上傳是單次請求、沒有續傳，而手機網路會斷。

- [ ] 用行動網路上傳一支 30MB 以上的影片，觀察進度是不是真的在動
- [ ] 上傳到一半切到別的 App 再切回來
- [ ] 上傳到一半按「取消」→ 回得了首頁，且不會留下打不開的空房間
- [ ] 正式專案若是免費方案：確認實際可上傳的大小（可能是 50MB 而非 100MB），
      並把 README 與首頁的數字改成實際值
